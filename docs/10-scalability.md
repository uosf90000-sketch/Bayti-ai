# 10. Scalability Plan — خطة التوسع

## 1. المبدأ

نحن **لسنا** منتج latency حرج مثل الشات العام — المستخدم يقبل أن "المجلس يعمل" دقائق. عنق الزجاجة الحقيقي هو **إنتاجية خط المعالجة (Throughput) وتكلفته**، لا زمن الاستجابة. لذلك التصميم كله queue-first، وكل توسيع هو "المزيد من الـ workers".

## 2. خصائص الحمل

| العبء | النمط | الاستراتيجية |
|-------|-------|--------------|
| API (CRUD/عرض) | خفيف، قابل للـ cache | Stateless replicas + CDN |
| Floorplan parsing | CPU/GPU متوسط، 30–90 ث | Worker pool مستقل |
| مجلس الوكلاء | LLM-bound، 2–5 دقائق | تواز داخلي + طوابير بأولوية |
| توليد الصور | GPU ثقيل، الأغلى | طابور منفصل + GPU autoscaling to zero |
| Catalog ingestion | دفعي ليلي | Spot instances |
| المحادثة/التعديل | تفاعلي (ثوانٍ) | طابور high-priority مخصص |

## 3. مراحل التوسع (نبني لما بعد المرحلة الحالية بواحدة فقط)

### المرحلة A — حتى ~1k مشروع/شهر (الإطلاق)
- كل شيء على مزود PaaS بسيط أو K8s صغير: API ×2, Workers ×N, Postgres managed (primary + replica), Redis managed.
- GPU عبر serverless inference (Replicate/Modal/RunPod) — **ندفع بالاستخدام، صفر GPU خامل.**
- التكلفة هنا هي المعركة: caching نتائج الوكلاء، Haiku للمهام البسيطة، prompt caching.

### المرحلة B — حتى ~50k مشروع/شهر (نمو السعودية + الخليج)
- K8s مع HPA على عمق الطوابير (KEDA) — الـ workers تتوسع بعدد الرسائل لا بالـ CPU.
- Postgres: read replicas للواجهات؛ فصل قاعدة الكتالوج عن قاعدة المشاريع (أنماط وصول مختلفة جذريًا).
- OpenSearch للكتالوج (فلترة+بحث هجين) مع بقاء pgvector للـ embeddings أو نقلها معه.
- CDN لكل الصور المولدة + تحويل صيغ (AVIF).
- GPU مخصص محجوز للحمل الأساسي + serverless للذروة (hybrid).

### المرحلة C — عالمي (مئات آلاف المشاريع/شهر)
- Multi-region: منطقة الخليج أساسية + أوروبا/آسيا للقراءة أولًا؛ كتالوج لكل سوق أصلًا مفصول بـ `country_code`.
- تقسيم الخدمات فعليًا (الحدود جاهزة من الـ Modular Monolith): floorplan-service, council-service, catalog-service.
- Data residency لكل دولة تتطلبه — البنية متعددة المستأجرين بالعمود `country_code` تسمح بالتقسيم.
- نماذج مملوكة مضبوطة (fine-tuned) للمهام عالية التكرار → خفض COGS ورفع الدقة معًا.

## 4. توسّع قاعدة البيانات

- الأحجام المتوقعة: المشاريع صغيرة نسبيًا (آلاف الصفوف/مشروع)؛ الضخم هو **الكتالوج** (ملايين المنتجات × تاريخ أسعار).
- `product_prices`: جدول append-only → partitioning شهري من اليوم الأول تقريبًا مجاني.
- `ai_usage`: partitioning شهري + تجميع (rollups) وأرشفة بعد 90 يومًا.
- JSONB الكبيرة (تقارير الوكلاء): تُنقل إلى S3 بعد 90 يومًا مع مؤشر (البيانات الحية تبقى نحيفة).

## 5. توسّع طبقة الذكاء الاصطناعي

- **Model routing حسب التعقيد:** غرفة نوم بسيطة → نموذج أرخص؛ مجلس مركب → الأقوى. القرار آلي بحسب حجم/تعقيد المدخل.
- **Batching:** توسيم الكتالوج وembeddings دفعات (Batch APIs أرخص 50%).
- **إعادة الاستخدام:** غرف متشابهة (نفس النوع/المساحة/النمط) تبدأ من قالب مخزّن ثم تُخصَّص — لا توليد من الصفر كل مرة.
- rate limits المزودين: تعدد مزودين عبر الطبقة الموحدة + طوابير تحترم حصص كل مزود.

## 6. أهداف أداء (SLOs)

| المقياس | الهدف |
|---------|-------|
| توافر API | 99.9% |
| P95 عرض صفحات النتائج | < 800ms |
| P95 تحليل مخطط | < 90s |
| P95 جولة المجلس كاملة | < 5min |
| P95 تعديل محادثة (نصي) | < 15s |
| فشل نهائي للـ jobs (بعد retries) | < 0.5% |
| تكلفة AI لكل مشروع كامل | سقف مُدار كـ KPI ربع سنوي |

## 7. تحمّل الأعطال

- كل job idempotent + retry بexponential backoff + DLQ مع تنبيه.
- فشل وكيل واحد لا يفشل المشروع: degrade gracefully (مثال: فشل HVAC → التصميم يصدر مع بند "التكييف قيد المراجعة" ويُستكمل لاحقًا).
- فشل مزود LLM → failover تلقائي للمزود الثاني عبر الطبقة الموحدة.
- Chaos-lite: اختبار قطع Redis/مزود LLM على staging ربع سنويًا.
