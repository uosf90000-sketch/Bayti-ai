# 9. Security Architecture — معمارية الأمان

## 1. نموذج التهديد (ما الذي نحميه؟)

| الأصل | الحساسية | التهديد الرئيسي |
|-------|----------|------------------|
| مخططات المنازل | **عالية جدًا** — تكشف تصميم بيت العائلة وعنوانها أحيانًا | تسريب، وصول غير مصرح |
| بيانات العائلة (أطفال/كبار سن/ميزانية) | عالية — PII | تسريب، بيع بيانات |
| كتالوج المنتجات + الأسعار | أصل تجاري | سرقة scraping شامل |
| Prompts والـ pipeline | ملكية فكرية | prompt injection، تسريب |
| حسابات المستخدمين | مالية (اشتراكات) | استيلاء حساب |

## 2. الهوية والوصول

- مصادقة B2C: **OTP عبر SMS** (السائد سعوديًا) + بريد اختياري؛ B2B: API Keys بنطاقات + mTLS اختياري.
- JWT access قصير العمر (15 دقيقة) + refresh rotation مع كشف إعادة الاستخدام.
- RBAC بسيط: `user`, `pro_designer`, `b2b_partner`, `admin` — و**عزل صارم بالمستأجر**: كل استعلام مشروط بـ `user_id` على مستوى الـ repository layer (وليس اجتهاد كل endpoint)، مع اختبارات عزل آلية.
- Admin: SSO + MFA إلزامي + سجل تدقيق لكل فعل.

## 3. حماية البيانات

- **التشفير:** TLS 1.3 عبر الكل؛ at-rest على DB وS3 (KMS)؛ المخططات في bucket خاص بوصول عبر presigned URLs قصيرة العمر (15 دقيقة) فقط.
- **تقليل البيانات:** لا نطلب عنوانًا دقيقًا — المدينة تكفي للتسعير.
- **الاحتفاظ:** حذف الحساب = حذف نهائي فعلي للمخططات والملفات خلال 30 يومًا (soft ثم hard delete مجدول).
- **التدريب على بيانات المستخدم:** opt-in صريح منفصل، وبعد إزالة الهوية.
- **الامتثال:** PDPL (السعودية) — سجل معالجة، وأساس نظامي لكل معالجة؛ إقامة البيانات في المنطقة (سحابة لها region سعودي/خليجي)؛ جاهزية GDPR للتوسع.

## 4. أمان طبقة الذكاء الاصطناعي (LLM Security)

- **Prompt Injection عبر المخططات:** المخطط مدخل غير موثوق — قد يحوي نصًا خبيثًا ("تجاهل التعليمات..."). المعالجة: فصل صارم بين تعليمات النظام والمحتوى المستخرج (delimiters + معاملته كبيانات)، وعدم تمرير نص حر من الملف إلى أي أداة تنفيذية.
- **مخرجات مقيدة:** كل وكيل مُجبر على JSON Schema — الرفض الآلي لأي خروج عن البنية يقطع معظم هجمات الحقن عمليًا.
- **لا أدوات خطرة للوكلاء:** الوكلاء لا يملكون وصول شبكة/DB مباشر؛ Shopping AI يقرأ من كتالوجنا الداخلي فقط، لا يتصفح الويب وقت الطلب.
- **حقن عبر بيانات المتاجر:** وصف منتج مخترق قد يحمل حقنًا — التنظيف في Ingestion + معاملة نصوص الكتالوج كبيانات دائمًا.
- **حدود إنفاق:** ميزانية tokens لكل مشروع + circuit breaker على الحلقات (وكيل يعيد المحاولة بلا نهاية).
- **خصوصية في الـ prompts:** لا يُرسل للـ LLM إلا ما يحتاجه الوكيل (لا هاتف/بريد المستخدم أبدًا).

## 5. أمان التطبيق

- OWASP ASVS L2 كخط أساس؛ فحص SAST + dependencies (Dependabot/Snyk) في CI.
- الرفع: فحص نوع الملف الفعلي (magic bytes لا الامتداد)، حد حجم، معالجة الـ PDF/DWG في sandbox معزول (ملفات CAD مشهورة كناقل exploits).
- Rate limiting متعدد الطبقات (IP، مستخدم، endpoint) + WAF على الحافة.
- CSP صارم، cookies `HttpOnly/Secure/SameSite`, CSRF tokens للواجهة.
- الدفع: لا نلمس بيانات البطاقات إطلاقًا — مزود دفع معتمد (PCI DSS عليه).
- Secrets: مدير أسرار (لا env في الريبو أبدًا) + دوران دوري.

## 6. أمان البنية والتشغيل

- شبكات خاصة: DB وRedis وWorkers بلا IP عام؛ الوصول الإداري عبر bastion/SSO.
- صلاحيات سحابية least-privilege لكل خدمة (IAM per-service).
- صور حاويات مفحوصة وموقعة؛ لا `latest` في الإنتاج.
- سجلات تدقيق مركزية غير قابلة للتعديل (من ضمنها كل وصول لمخططات المستخدمين).
- خطة استجابة للحوادث: severity levels، مسؤول مناوب، قالب إبلاغ المستخدمين (التزام PDPL بالإبلاغ عن التسريبات).

## 7. أمان الكتالوج (اتجاه معاكس)

- حماية كتالوجنا من scraping شامل: rate limiting + توقيع طلبات الواجهة؛ الـ API العام للكتالوج (B2B) بمفاتيح ومحاسبة.
- احترامنا نحن للمتاجر: robots.txt، معدلات مهذبة، وأولوية دائمة للاتفاقيات الرسمية على الـ scraping (مخاطرة قانونية — انظر وثيقة المخاطر).

## 8. خارطة أمان مرحلية

| المرحلة | الإجراء |
|---------|---------|
| MVP | كل ما سبق أساسيًا + pentest خارجي واحد قبل الإطلاق العام |
| نمو | برنامج bug bounty خاص، SOC2 Type I (لعقود B2B) |
| توسع | SOC2 Type II، تدقيق PDPL خارجي، عزل بيانات لكل دولة عند الحاجة التنظيمية |
