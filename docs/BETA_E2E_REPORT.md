# تقرير اختبار E2E — Beta التفعيل الإنتاجي

> آخر تحديث: 2026-07-16 · الفرع: `claude/bayti-ai-platform-kf18m3` · آخر commit: `5449758`

## ملخص تنفيذي

المطلوب: تفعيل إنتاجي حقيقي (Railway env + Supabase حقيقي) واختبار E2E حقيقي من
Railway. **الحقيقة الصادقة أولًا:** هذه الجلسة (Claude Code) **لا تملك وصولًا** إلى
لوحة Railway (متغيرات البيئة/النشر) ولا إلى مشروع Supabase حقيقي (بيانات اعتماد) —
نفس الفجوة الموثّقة مرتين سابقًا (`ANTHROPIC_API_KEY` في `docs/FLOORPLAN_ANALYSIS.md`،
Supabase الحقيقي في `supabase/README.md`). ما تم فعليًا في هذه المرحلة:

1. **تجهيز كامل** لمتغيرات Railway (موثّقة بدقة، بلا أي سر في Git).
2. **تحصين حقيقي** لكل مسار يستدعي Anthropic (timeout + retry + تصنيف أخطاء + logging آمن).
3. **مخطط Supabase حقيقي كامل** لكل مخرجات الأنابيب (Room Objects/Design/Shopping/Cost/Versions) + ربطه الفعلي في الكود خلف flag — **جاهز للتفعيل الفوري** بمجرد توفر بيانات اعتماد حقيقية، لكن لم يُفعَّل فعليًا (لا بيانات اعتماد في هذه البيئة).
4. **اختبار E2E حقيقي محليًا** (متصفح فعلي، Playwright) — وليس من Railway (لا نشر تم تنفيذه من هذه الجلسة؛ النشر الفعلي يدوي حصرًا من لوحة Railway، قرار مؤسس سابق).
5. **اختبار كل حالات الفشل الثمانية المطلوبة فعليًا** — نتائج مفصّلة أدناه.
6. **بوابة "مكتمل"** مُطبَّقة ومُختبَرة (12/12 اختبار وحدة حقيقي + تأكيد متصفح).

## 2) تحصين مسارات Anthropic — منجز وحقيقي

`apps/web/lib/ai/client.ts` (جديد) يُستخدم من `analyzeFloorplan.ts` و`designEngine.ts`:

| المطلوب | التنفيذ | التحقق |
|---|---|---|
| Server-side فقط | لا تغيير — كان صحيحًا أصلًا، `ANTHROPIC_API_KEY` لا يُقرأ إلا داخل هذين الملفين خلف Route Handlers | Build نظيف (لا كسر لحد server/client) |
| لا كشف للمفتاح للمتصفح | مؤكد بنيويًا — لا استيراد لهذين الملفين من أي client component | فحص بصري + build |
| Timeout | `timeout: 45_000` صريح في بناء عميل SDK (وليس الافتراضي الصامت) | اختبار وحدة حقيقي: تصنيف `APIConnectionTimeoutError` → رسالة عربية صحيحة |
| Retry محدود | `maxRetries: 2` صريح (آلية SDK نفسها — يعيد فقط على أخطاء قابلة للتكرار فعليًا: انقطاع اتصال، 408/409/429/5xx — لا يعيد أبدًا على 4xx) | نفس الاختبار أعلاه |
| رسائل خطأ عربية واضحة | `classifyAnthropicError()` يميّز 6 فئات فشل حقيقية (مهلة، تجاوز حد، مفتاح غير صالح، خدمة غير متاحة، انقطاع اتصال، طلب غير صالح) بفئات SDK الفعلية (`instanceof`)، لا مطابقة نصوص | اختبار وحدة حقيقي: 5/5 رسائل صحيحة |
| Logging بلا بيانات حساسة | `logAiCall()` يسجل فقط `{op, status, durationMs, errorClass}` — لا صورة، لا نص مولَّد، لا مفتاح | مراجعة كود مباشرة |

**اكتشاف حقيقي أثناء الاختبار:** محاولة أولى لاختبار `classifyAnthropicError` باستيراد ثابت لحزمة `@anthropic-ai/sdk` بجانب استيرادها الديناميكي الداخلي أنتجت نسخة وحدة مزدوجة تحت `tsx` (فشل `instanceof` كاذبًا). أُعيد الاختبار باستيراد ديناميكي متسق (مطابق تمامًا لأسلوب الكود الفعلي في التطبيق) فنجحت كل الحالات — تأكيد أن الكود الحقيقي (الذي يستخدم استيرادًا ديناميكيًا في كل مكان) سليم، والمشكلة كانت في منهجية الاختبار الأولى فقط.

**إضافة استباقية:** توجيه صريح في System Prompt لتحليل المخططات لحالتي "PDF متعدد الصفحات" و"صورة غير واضحة" (تجاهل أغلفة/مخططات موقع، جمع طوابق منفصلة كغرف مستقلة بلا تكرار؛ تقرير ثقة منخفضة صراحة بدل رفض الاستجابة) — **لم يُختبَر فعليًا ضد Claude حقيقي** (لا مفتاح)، لكن مسار الرفع الفعلي لملف PDF متعدد الصفحات حتى نقطة استدعاء Claude تم اختباره فعليًا (انظر §5).

## 3) Supabase الحقيقي — مخطط وربط جاهزان، غير مفعَّلين فعليًا

### ما تم بناؤه (جديد كليًا هذه الدفعة)

`supabase/migrations/0003_design_pipeline.sql` — 6 جداول جديدة، كلها بـ RLS عبر `projects.user_id`:

| الجدول | يحفظ |
|---|---|
| `floorplan_analyses` | نتيجة تحليل المخطط (المصدر، الثقة الإجمالية) |
| `room_objects` | **كل Room Object مستقل** (النوع، الاسم، المساحة، الأبعاد، الثقة) |
| `room_designs` | **Design Results** لكل غرفة (أسلوب، لوحة ألوان، مواد، أثاث، إضاءة) |
| `shopping_matches` | **Shopping Matches** — عنصر التصميم الأصلي + المطابقة (منتج حقيقي أو `matched=false` صراحة) |
| `cost_summaries` | **Cost Summary** — إجمالي المشروع، التوزيع حسب الغرفة/الفئة |
| `project_versions` | **Versions** — لقطة كاملة غير قابلة للتعديل لكل تشغيلة (P7: لا حذف، لا تعديل — إدراج وقراءة فقط) |

`apps/web/lib/supabase/repositories/pipeline.ts` (جديد) يربط كل هذا بعمليات Supabase حقيقية. `twin.ts`/`design/pipeline.ts` يستدعيان هذا الريبو تلقائيًا عندما `!flags.USE_MOCK_PROJECTS` — **بنفس نمط VS-4 المعتمد مسبقًا تمامًا** (fail-loud: تفعيل الـ flag بلا بيانات اعتماد حقيقية يرمي خطأً واضحًا فورًا، لا سقوط صامت لبيانات محلية).

### الحاجز الوحيد المتبقي

لا بيانات اعتماد Supabase حقيقية في هذه البيئة، **ولا مصادقة Supabase حقيقية مبنية بعد** (نقطة موثّقة مسبقًا في `supabase/README.md` منذ VS-4 — تسجيل الدخول الحالي OTP تجريبي محلي فقط، ليس جلسة Supabase حقيقية). أي تفعيل حقيقي لهذه الشريحة يحتاج الاثنين معًا: بيانات اعتماد Supabase + مصادقة حقيقية — كلاهما خارج نطاق هذه الجلسة ومُعلَنان بوضوح، وليسا مفاجأة جديدة.

**ما يعنيه هذا عمليًا:** الحفظ إلى Supabase الحقيقي **جاهز 100% كودًا** لكل عنصر طلبه المؤسس (مشروع، ملف، تحليل، Room Objects، Design Results، Shopping Matches، Cost Summary، Versions) — تفعيله الفعلي خطوة تشغيلية بحتة (توفير مشروع Supabase + قلب flag)، لا تتطلب أي تغيير كود إضافي.

## 4) بوابة "مكتمل" — مُطبَّقة ومُختبَرة فعليًا

`apps/web/lib/design/complete.ts` (جديد): `isPipelineComplete(twin, pipeline)` تتحقق من الأربعة شروط دون استثناء:

1. توجد نتيجة محفوظة (`pipeline`) مرتبطة بنفس `project_id` للتوأم المحمَّل.
2. عدد الغرف في النتيجة **يطابق تمامًا** عدد الغرف المكتشفة في التوأم — لا أكثر، لا أقل.
3. كل غرفة في التوأم موجودة في النتيجة (يمنع بيانات مسربة من توأم/مشروع آخر).
4. كل غرفة نجح توليد تصميمها فعليًا (`design !== null`) **و**لا يوجد خطأ معلّق عليها.

التكلفة نفسها مضمونة الصدق بنيويًا (Cost Engine لا يملك أي مسار لرقم مُخترع — انظر §5).

**اختبار حقيقي (12/12 نجح)** عبر سكربت استورد `costForRoom`/`computeProjectCost`/`isPipelineComplete` الفعلية من المستودع (لا إعادة تطبيق):
- ✅ مشروع صحيح كليًا (غرفة واحدة، تصميم ناجح، project_id وعدد الغرف متطابقان) → `مكتمل = true`
- ✅ غرفة واحدة فشلت ضمن مشروع بغرفتين → `مكتمل = false`
- ✅ عدد الغرف في النتيجة أقل من التوأم (بيانات ناقصة/مسربة) → `مكتمل = false`
- ✅ `project_id` مختلف بين التوأم والنتيجة (نتيجة من مشروع آخر) → `مكتمل = false`

**تأكيد متصفح فعلي:** تشغيل خط الإنتاج الحقيقي على مشروع فيلا النرجس (6 غرف، كلها فشلت بلا مفتاح API) أظهر **"⏳ غير مكتمل — راجع الغرف أدناه"** بدلًا من أي ادّعاء اكتمال كاذب — لقطة شاشة موثّقة أثناء التطوير.

## 7) ما هو حقيقي الآن (بلا Demo)

- اكتشاف عدد/نوع الغرف عبر Claude Vision فعلي (خط أنابيب كامل، يحتاج فقط المفتاح).
- توليد تصميم لكل غرفة عبر Claude فعلي (نفس الحال).
- مطابقة تسوق ضد كتالوج حقيقي فعلي (61 منتجًا معتمدًا، لم يُعدَّل).
- حساب تكلفة من أسعار حقيقية فقط — لا رقم مُخترع في أي مسار، مُختبَر صراحة.
- تصدير CSV/PDF من بيانات الأنابيب الفعلية فقط.
- Timeout/retry/تصنيف أخطاء/logging آمن — كلها فعلية ومُختبَرة.
- مخطط Supabase الكامل لكل مخرجات الأنابيب — جاهز، الكود يستدعيه فعليًا خلف flag.

## 8) ما يزال محدودًا

- **لا Railway حي** — لم يُنشر شيء من هذه الجلسة؛ لا رابط للاختبار عليه.
- **لا Supabase حقيقي مفعَّل** — المخطط والكود جاهزان، ينقص فقط بيانات اعتماد حقيقية + مصادقة Supabase حقيقية (فجوة معروفة من VS-4).
- **لا اختبار حي ضد Claude حقيقي** — كل ما تحقق هو مسار الفشل الصحيح (بلا مفتاح)؛ مسار النجاح (تحليل/تصميم فعلي) لم يُختبَر لعدم توفر مفتاح.
- **التوأم الرقمي مبسّط** (لا هندسة CAD كاملة) — قرار نطاق سابق موثَّق في `docs/FLOORPLAN_ANALYSIS.md`.
- **3D تخطيطي** وليس دقيقًا هندسيًا — قرار نطاق سابق موثَّق في `docs/DESIGN_PIPELINE.md`.
