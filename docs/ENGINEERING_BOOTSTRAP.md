# Engineering Bootstrap — من الوثائق إلى أول سطر كود

> خطة الانتقال الرسمية من Architecture v1.0 (Frozen) إلى التنفيذ. **القاعدة الحاكمة (قرار مؤسس): لا يُكتب أي كود إنتاجي قبل اكتمال واعتماد الأقسام 7–12.**

---

## 1. ترتيب تنفيذ الأقسام 7–12 (كتابةً واعتمادًا)

الترتيب مبني على التبعيات، لا على أرقام الفهرس:

| # | القسم | لماذا بهذا الترتيب | يُغلق من الديون |
|---|-------|----------------------|-------------------|
| **7** | التسوق وتكامل الكتالوج (Ingestion، التوحيد، Embeddings، تنفيذ عقد 6.22، APIs الكتالوج) | أطول lead time غير هندسي (اتفاقيات المتاجر — RSK-03) يجب أن تنطلق مواصفاته أولًا | جزء من TD-01 (كتالوج/API) |
| **8** | المخرجات (الرندر الموجه بالتوأم، الفيديو، 3D، تقرير PDF) | يعتمد على التوأم المجمد فقط — مستقل عن 7؛ وهو موطن لحظات الانبهار ([WOW_MOMENTS](WOW_MOMENTS.md)) | TD-01 (rendering) |
| **9** | التعديل بالمحادثة (Intent Parser، Edit Router فوق ADR-031، عقود SSE) | يحتاج 7+8 مكتملين ليعرّف أثر التعديل على التسوق والرندر | TD-01 (chat) |
| **10** | الحسابات والباقات والتسعير | **يُقفل F-11:** التسعير يُبنى على نموذج COGS المكتمل من 7–9 | TD-01 (billing) |
| **11** | المتطلبات غير الوظيفية الموحدة (يعيد اعتماد وثائق الأمن/التوسع/الأداء فوق الأساس المجمد) | تجميع ما تناثر + إغلاق فجوات مراجعة NFR في الـ Freeze | TD-01 (docs 09/10/11) |
| **12** | خارج النطاق، معايير القبول النهائية، وبوابات الإطلاق (يعيد كتابة MVP والـ Roadmap) | الخاتمة — لا يُكتب قبل استقرار كل ما قبله | TD-01 (docs 08/13) |

- كل قسم بنفس المنهجية: كتابة → مراجعة مؤسس → اعتماد → تحديث ADR/القاموس إن لزم.
- **إيقاع مستهدف:** قسم كل 1–2 جولة مراجعة؛ حارس RSK-10: أي قسم يتجاوز دورتي مراجعة → تجميد نطاقه والدفع للاعتماد.

## 2. نقطة "اكتمال التوثيق" (Documentation Complete Gate)

تتحقق عندما: ① الأقسام 7–12 معتمدة ② TD-01 مُغلق (وثائق الجيل الأول أُعيدت كتابتها أو أُحيلت رسميًا) ③ TD-02 مُغلق (Traceability كملف مُدار) ④ TD-08 مُنفذ (تقسيم الـ PRD لملفات) ⑤ مصادقة مؤسس واحدة أخيرة: **"Documentation Complete — Go to Build"**.

## 3. أول Sprint بعد البوابة — Sprint 0 "الأساس والقياس" (أسبوعان)

> **هنا يُسمح بأول سطر كود — وليس قبله.** استثناء وحيد قائم الآن: جمع مخططات Golden Set والتفاوض مع المتاجر (عمل بيانات وأعمال، ليس كودًا) يجريان بالتوازي مع كتابة الأقسام.

| مسار | التسليم في نهاية Sprint 0 |
|------|-----------------------------|
| **Spike القياس (الأولوية المطلقة — يحسم RSK-01/02)** | تحليل 20 مخططًا حقيقيًا بالمسار الهجين + جولة مجلس مصغرة (3 وكلاء) على مخطط واحد → تقرير: دقة فعلية، زمن فعلي، تكلفة فعلية مقابل ميزانيات 4.14/4.22/6.7 |
| الأساس | Monorepo وفق [هيكل 07](07-folder-structure.md) المحدث + CI/CD + بيئة dev بأمر واحد + بيئة staging |
| العقود | `packages/design-schema` v1: **الـ schemas المجمدة تُنقل كما هي** (DigitalTwin، AgentRun، Proposal، DecisionExplanation…) بفحص توافق CI |
| طبقة LLM | الطبقة الموحدة (providers، تسجيل تكلفة، prompt versioning) — شرط لكل ما بعدها |
| البيانات | Golden Set: 30+ مخططًا موسومة (اكتمال 70 خلال Sprint 1–2) |

## 4. نقاط التحقق بين الـ Sprints (البوابات — لا انتقال دونها)

| البوابة | بعد | معيار العبور (من الوثائق المجمدة) |
|---------|-----|-------------------------------------|
| **G-0: Reality Check** | Sprint 0 | تقرير الـ Spike: الانحراف عن الميزانيات ≤ 50%؛ إن تجاوز → **مراجعة نطاق MVP قبل أي بناء واسع** (خطة RSK-02 المعتمدة) |
| **G-1: Twin Gate** | بناء مسار التحليل (Sprints 1–4 تقريبًا) | AC-1…AC-8 على Golden Set (دقة غرف ≥85% raster/95% CAD، معايرة ثقة، استئناف انتقائي مُختبر) — **بوابة R1 الوجودية** |
| **G-2: Council Gate** | بناء المجلس | E2E-2 "فيلا النرجس" يعمل آليًا في CI بكل مراحله العشر + F2E-1 (حالة الفشل) تمر |
| **G-3: Commerce Gate** | الكتالوج والتسوق | معايير G4: ≥80% عناصر بمنتج حقيقي بسعر ≤72 ساعة، روابط صالحة ≥95%، 3 متاجر فعلية |
| **G-4: Experience Gate** | الواجهة والمخرجات | مصفوفة قبول القسم 3 (10 مستخدمين حقيقيين، 8+ يكملون بلا مساعدة) + عينة WOW_MOMENTS تعمل فعلًا |
| **G-5: Launch Gate** | قبل الإطلاق العام | بوابات القسم 12 المعتمدة + pentest + تمرين DR + لوحات المراقبة حية بمالكين |

- **إيقاع ثابت:** Sprints أسبوعان · demo داخلي كل نهاية sprint · لا يُدمج PR بدون مراجعة + evals خضراء · كل بوابة تُوثَّق نتيجتها في تقرير موقّع بتاريخ.

## 5. معايير الانتقال بين المراحل (ملخص القاعدة)

1. **وثيقة → كود:** فقط عبر بوابة Documentation Complete (بند 2).
2. **Sprint → Sprint:** فقط عبر بوابته في الجدول أعلاه — بوابة حمراء توقف التقدم وتفتح خطة تصحيح، لا "نكمل ونصلح لاحقًا".
3. **كود → إنتاج:** evals خضراء + Agent Scorecard بلا تراجع هندسي (6.24) + shadow للقواعد الجديدة.
4. **أي تغيير معماري في أي لحظة:** ADR جديد بمصادقة المؤسس أولًا (قاعدة الـ Freeze).

## 6. متى يُسمح بكتابة أول سطر كود؟ (الإجابة الرسمية القاطعة)

> **بعد اعتماد المؤسس للأقسام 7–12 كاملة، وإغلاق TD-01/02/08، ونطق بوابة "Documentation Complete — Go to Build" — عندها يبدأ Sprint 0، وأول كود يُكتب هو Spike القياس وطبقة العقود، بهذا الترتيب.**
> كل ما قبل ذلك وثائق وبيانات واتفاقيات فقط. هذه القاعدة نفسها ضمن "ما يُمنع تغييره" في مذكرة الإصدار.
